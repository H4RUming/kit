# SK하이닉스 AI 해커톤 2026 회고

개인 참가. 2차 예선(크래프톤 Cofa-Probe) 대비용으로 이 하네스(kit)를 만들고, 실전에 두 번 응시한 뒤 정리한 회고.

| 문제 | 한 일 | 결과 |
| --- | --- | --- |
| 제공된 Codex만 쓰는 180분 실무형 과제. Computer Use 금지, 토큰 사용량도 평가에 반영. | 규칙 파일, 작업 문서 템플릿, 검증 스크립트 5개, 지시 카드로 하네스 구성. 1차 응시 후 문제점 보완. | 1차 예선 합격, 2차 예선 탈락. |

과제 내용은 대회 규정상 비공개라 작업 방식 위주로 정리함.

## 시험 환경

- 평가 축은 기술 관리, 의도 관리, 인지 관리 3개
- 180분 과제 뒤 제출물 기반 서술형 문항 (문항당 5분, AI 사용 불가)
- AI는 제공된 Codex만 사용 가능. 공개 GitHub 저장소는 clone 가능
- Computer Use, 플랫폼 설정 변경 금지
- 대화 기록, 터미널, git 로그, 테스트 결과, 작업 문서를 모두 수집해 평가

AI에게 어떻게 일을 시켰는지도 평가 대상이라, 판단 과정이 파일로 남도록 설계함. 제공 모델 성능이 높지 않고 토큰도 추적되니 모델이 읽는 양을 최대한 줄이는 쪽을 택함.

## 하네스 설계

```
<과제 루트>/
  AGENTS.md         Codex 규칙 (세션 시작 시 자동 로드)
  work/
    TASK.md         요구사항, 제약, 완료 조건
    DECISIONS.md    결정과 근거 (직접 작성)
    HANDOFF.md      세션 인계
    VERIFY.md       검증 기록 (자동 생성)
  .kit/
    tools/          검증 스크립트
    prompts/        단계별 지시 카드
    docs/           웹, DB, 인증 관련 세부 규칙
```

과제 폴더에서 clone 후 `install.sh`만 실행하면 위 구조가 만들어짐.

**AGENTS.md는 짧게.** 처음엔 91줄이었는데 모델이 중간 규칙을 자꾸 놓쳐서 47줄로 줄임. 반드시 지켜야 할 규칙 6개와 작업 순서만 남기고, 웹이나 DB 관련 규칙은 `docs/`로 빼서 필요할 때만 읽게 함. `킥오프`, `C1 진행`, `리뷰` 같은 단축어로 지시 카드를 부르게 만듦.

과설계 방지 규칙은 [Ponytail](https://github.com/DietrichGebert/ponytail)(MIT)을 참고해 번역함.

### 검증 스크립트

시험 환경에 뭐가 설치돼 있을지 몰라서 전부 Python 표준 라이브러리로만 작성.

| 스크립트 | 용도 |
| --- | --- |
| `peek.py` | CSV, JSON, SQLite 등을 통째로 열지 않고 구조만 요약. 실행 환경 점검 |
| `t.py` | 테스트 결과를 요약해 출력하고 VERIFY.md에 기록. 파일 변경 없이 재실행하면 막고, 같은 실패가 반복되면 경고 |
| `q.py` | pip install처럼 출력이 긴 명령은 로그 파일로 빼고 에러 줄만 표시 |
| `webcheck.py` | 브라우저 없이 HTTP 요청으로 웹 기능 확인. 버그 9개를 일부러 넣은 테스트 앱에서 9개 모두 검출 |
| `dbcheck.py` | CSV를 DB에 넣은 뒤 행 수, 합계, 키 누락을 대조. 누락, 소수점 잘림 등 4가지 버그 검출 |

MCP 서버로 만드는 것도 고민했지만, 사전 체험이 1회뿐이라 시험장에서 연결될지 확인할 방법이 없어 CLI 스크립트로 감. 스크립트는 내가 다른 터미널에서 직접 돌릴 수도 있어서 토큰 절약에도 도움이 됨.

## 1차 응시 (10/31)

플랫폼 접속 장애로 시험 전체가 중단됨. 연습이라 생각하고 끝까지 제출해 서술형까지 풀어봤고, 여기서 문제가 꽤 많이 나옴.

| 겪은 문제 | kit에 반영한 것 |
| --- | --- |
| 매번 전체 테스트를 돌려 오래 걸리고, 테스트끼리 상태가 섞여 결과도 믿기 어려움 | 조건별로 해당 테스트만 실행, 테스트마다 독립된 상태에서 실행 |
| 인계 문서를 쓰기 전에 컨텍스트(256k)가 차서 자동 압축이 먼저 일어남 | 조건 하나 끝날 때마다 HANDOFF의 현재 상태를 짧게 갱신 |
| 계획과 다르게 구현됐는데 시간에 쫓겨 그냥 넘김 | 구현 전에 함수 구조를 먼저 보여주고 확인받는 단계 추가 |
| 계획서에 제약사항 칸이 없어 중간에 README를 다시 읽혀야 했음 | TASK 템플릿에 요구사항 출처, 제약, 검증 방법 칸 추가 |
| 담당자에게 물은 것 상당수가 이미 README에 있던 내용 | 엣지 케이스 위주로 묻는 인터뷰 체크리스트로 변경 |

도구로 해결할 수 없는 문제도 남음.

- 조건 하나에 10~20분씩 걸림. 조건 단위가 너무 컸음.
- 서술형 6문제 중 자신 있게 답한 건 2개. AI가 만든 코드를 이해하지 못한 채 제출한 게 그대로 드러남.

## 2차 응시 (11/5)

### 나아진 점

- 담당자에게서 필요한 정보를 이번엔 전부 받아냄. 1차 때는 몇 개를 놓쳤음.
- AI가 설계나 구현에서 이상하게 판단한 부분을 중간중간 잡아서 고침.
- 핵심 로직은 직접 깊게 파서 서술형에서 설명하기 편했음. 질문이 더 어려워졌는데도 2~3문제는 제대로 답함.

### 아쉬운 점

- 담당자에게 확인할 게 1차보다 훨씬 많은 과제였음. 인터뷰와 계획에만 1시간 가까이 씀.
- 핵심 로직과 테스트에 또 1시간을 쓰고 나서야 나머지 부분을 시작함. 연결까지만 하고 결과물을 직접 써보지도 못함. 테스트상으로는 기능이 다 있었지만 사람이 쓸 수 있는 수준은 아니었음.
- 막판에 급해져서 가벼운 모델에 고속 모드까지 켰는데, 크레딧만 더 쓰고 후반 작업은 프로토타입 수준으로 끝남.
- Codex를 실전에서 거의 처음 써봄. 평소엔 Claude Code만 써서 명령어와 세션 관리가 손에 안 익었음.
- 서브에이전트를 제대로 못 씀. 따로 맡겨도 되는 작업을 한 세션에서 하나씩 처리함.
- Claude Code보다 응답이 느려 조건마다 기다리는 시간이 길었고, 이 때문에 시간이 더 빠듯해짐.
- 조건마다 3줄 요약을 받게 해둔 단계는 제대로 작동하지 않았음.

## 원인

**하네스 흐름이 순서대로 하나씩 처리하는 구조였음.** 1차 때 검증이 부실했던 게 마음에 걸려 조건 하나씩 확실하게 끝내는 쪽으로만 밀었고, 그러다 보니 결과물을 먼저 대충이라도 세워두는 단계가 빠짐.

**익숙한 쪽부터 손이 감.** 원래 핵심 로직 쪽이 편해서 자연스럽게 그쪽부터 시작했고, 테스트로 바로 확인되는 부분과 달리 직접 써봐야 확인되는 부분은 더 미루게 됨. 시험 시작 1시간쯤 뒤에야 작업을 나눠 병렬로 진행할 수 있었다는 걸 알았음.

**Codex 숙련도.** 느린 응답 속도를 감안해 시간을 나눴어야 했는데 그러지 못했고, 서브에이전트로 일을 나누는 것도 익숙하지 않았음.

**즉흥적인 모델 변경.** 막판에 모델을 바꾼 건 급한 마음에 한 결정이었음. 미리 정해둔 기준이 있었다면 하지 않았을 것.

| 첫 작업 | 가짜 데이터로 처음부터 끝까지 일단 동작하는 최소 버전 만들기 |

## 느낀 점

두 번 다 결과는 아쉬웠지만, 문제를 정의하고 AI를 통제하는 부분은 1차보다 나아짐. 1차 때는 필요한 정보를 다 끌어내지도 못했고 AI가 만든 걸 이해 못 한 채 냈는데, 2차에서는 둘 다 해냄.

하네스에 내 습관이 그대로 반영된다는 것도 알게 됨. 검증을 꼼꼼히 하려고 만든 규칙이 결과적으로 기능부터 파는 습관을 더 강하게 만들었음.

그리고 이유를 적어둔 부분은 나중에 전부 설명할 수 있었음. 서술형에서 막힌 건 대부분 기록을 남기지 않은 부분이었음.
